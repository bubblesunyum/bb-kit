Shipped Button, Card, CardLink, ListItem and List — bbk-rar.6 through .10, step 4 now 9/15.
Was mid-thought on bbk-u5p: List always renders plain ListItems, so CardListItem is only
reachable by hand-writing the <ul>, which is what List exists to prevent. Plan §3.5's prop
table gives List no variant, so I followed it rather than inventing API — but a `CardList`
named wrapper is Rule 4's own answer and I keep wanting to write it. That is the first thing
to decide.

The tempting wrong fix on bbk-kh1 is worth naming: when CardLink lands in a CardFooter the
overlay covers only the footer, and the obvious move is to stop CardFooter being positioned.
That breaks the thing CardFooter's position is *for* — lifting tag buttons above the overlay.
The two requirements genuinely fight (see the stretched-link-anchoring-fights-itself memory);
any fix has to pick a side, not split the difference.

Two things I could not judge from the source and only caught by looking at four-up captures:
bbk-abw (clash light makes primary and danger the same salmon, so DangerButton carries no
warning) and bbk-2vw (plain and raised rows are indistinguishable in all four palette/mode
combinations, not just forest light). Both are colour moves, both now have the evidence on
the bead. bbk-dv5 was explicitly waiting for real components to judge against — it has them
now, so that epic is genuinely unblocked in a way it was not yesterday.

back in bbk-rar.4; I only wrote it down. A fix means Surface publishing its padding as a
custom property, which adds a knob to Surface — worth deciding, not doing quietly.
